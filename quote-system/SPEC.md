# 製造業向け 見積半自動化システム — SPEC（MVP）

最終更新: 2026-07-23

---

## 1. 要件整理

### 1.1 背景と課題

現状の見積業務は以下の手作業で行われている。

1. 顧客から届いた図面を確認
2. 必要な部品・材料・加工内容を読み取る
3. 材料費・加工費・外注費などから原価を算出
4. 担当者の経験に基づき上乗せ金額・利益を決定
5. 見積価格を決定
6. Excel 等で見積書を作成

特に「どの程度利益を上乗せするか」が担当者の経験に依存しており、**属人化**している。

### 1.2 目的

- 見積作成のリードタイム短縮（AI による図面読み取り＋自動原価計算）
- 価格決定ノウハウのデータ化（AI 推奨値と担当者決定値の差分・理由を蓄積）
- 担当者を置き換えるのではなく **「AI が見積案を作成し、人間が確認・修正・承認する」半自動化**

### 1.3 設計思想（Human-in-the-loop）

```
AI 提案 → 人間確認 → 修正 → 承認
```

- AI の結果をそのまま確定値にしない。すべての AI 出力は編集可能。
- 原価計算は AI に計算させず、**プログラムの計算ロジック**として実装する。
- 「AI がなぜこの価格を提案したのか」（粗利率の内訳・原価の内訳）を必ず画面で確認できるようにし、ブラックボックス化を避ける。
- AI 推奨値・人間の最終決定値・差分・変更理由を必ず履歴として保存し、将来「ベテラン担当者が何を基準に価格を決めているか」を分析可能にする。

## 2. システム構成

```
┌──────────────────────────────────────────────┐
│ Next.js (App Router / TypeScript)            │
│                                              │
│  ┌─ 画面 (React Server/Client Components)    │
│  ├─ API Routes (/api/...)                    │
│  ├─ 計算ロジック  src/lib/cost.ts             │
│  │               src/lib/pricing.ts          │
│  └─ AI 抽象化層  src/lib/ai/                  │
│       ├─ types.ts      (共通インターフェース) │
│       ├─ provider.ts   (ファクトリ)          │
│       ├─ mock.ts       (MockProvider)        │
│       ├─ gemini.ts     (GeminiProvider)      │
│       └─ openai.ts     (OpenAIProvider)      │
├──────────────────────────────────────────────┤
│ Prisma ORM                                   │
├──────────────────────────────────────────────┤
│ SQLite (ローカルファイル dev.db)              │
│ 図面PDF: uploads/ ディレクトリ（Git管理外）    │
└──────────────────────────────────────────────┘
```

- **ローカル環境で完結**して動作する。外部送信は AI 解析実行時のみ（キー未設定時は MockProvider で外部送信ゼロ）。
- AI プロバイダは `AI_PROVIDER` 環境変数と API キーの有無で自動選択:
  - `GEMINI_API_KEY` があれば GeminiProvider
  - `OPENAI_API_KEY` があれば OpenAIProvider
  - どちらも無ければ **MockProvider**（ダミーデータ返却。開発・動作確認用）

### 2.1 セキュリティ設計

| 項目 | 対応 |
|---|---|
| API キー管理 | `.env` で管理。`.gitignore` 済み。`.env.example` を同梱 |
| 外部送信の分離 | 外部 API 呼び出しは `src/lib/ai/` 配下のみに限定 |
| 送信内容の確認 | 解析実行前に「どのプロバイダへ何を送るか」を画面に表示 |
| ログ | 図面の中身・API キーはログに出力しない（プロバイダ名とステータスのみ） |
| 図面ファイル | `uploads/` に保存し Git 管理外。DB にはパスのみ保存 |

## 3. DB 設計（Prisma / SQLite）

SQLite は enum 非対応のため、ステータス等は文字列で保持する。

### 3.1 案件・見積系

| テーブル | 役割 |
|---|---|
| `Project` | 案件。ID は `Q-YYYY-NNNN` 形式で自動発行。案件名 / 顧客名 / 担当者 / 希望納期 / 数量 / 備考 / 図面パス / ステータス |
| `DrawingAnalysis` | 図面解析結果。**AI の生出力（aiResultJson）と人間の修正後（editedJson）を別カラムで保持**（履歴要件） |
| `CostItem` | 原価明細行。category（material / process / purchased / outsource / other）、数量 × 単価 = 金額、source（auto / manual） |
| `CostAdjustmentLog` | 原価の手動修正履歴。修正前 / 修正後 / 修正理由 / 担当者 / 日時 |
| `MarginProposal` | 粗利提案。基準粗利率＋各種加算（小ロット / 短納期 / 特殊加工 / 難易度 / リスク / 顧客別 / 営業 / その他）→ 推奨粗利率・推奨売価 |
| `PriceDecision` | **経験値データ**。AI 推奨粗利率・価格 / 最終決定粗利率・価格 / 差分 / 変更理由 / 決定担当者 / 日時 |
| `OrderResult` | 受注 / 失注の結果と受注価格 |

### 3.2 マスタ系

| テーブル | 主な項目 |
|---|---|
| `MaterialMaster` | 材料コード / 材料名 / 材質 / 規格 / 単価 / 単位 / 更新日 |
| `ProcessMaster` | 加工コード / 加工名 / 単価 / 課金単位（分・回・個など） / 更新日 |
| `OutsourceMaster` | 外注工程名 / 外注先 / 基準単価 / 備考 / 更新日 |
| `PurchasedPartMaster` | 部品コード / 部品名 / 仕入単価 / 仕入先 / 更新日 |

### 3.3 ステータス遷移

```
新規 → 図面解析中 → 原価確認 → 見積作成中 → 承認待ち → 見積提出済 → 受注 / 失注
```

（MVP では手動で任意のステータスへ変更可能。厳密なワークフロー制御は第2フェーズ）

## 5. 主要ユーザーフロー

```
① 案件登録（/projects/new）
   案件名・顧客・数量などを入力し、図面PDFをアップロード
   → 案件ID（Q-YYYY-NNNN）自動発行、ステータス「新規」
        ↓
② 図面解析（案件ワークスペース > 図面解析タブ）
   送信内容とプロバイダを確認して「AI解析を実行」
   → AI が部品名・材質・寸法・加工方法などを JSON で抽出
   → 読み取れなかった項目は「要確認」表示
   → 担当者が全項目を確認・修正して保存（AI原文は別途保持）
        ↓
③ 原価計算（原価計算タブ）
   マスタから材料・加工・購入部品・外注を明細行として追加
   → 材料費＋加工費＋購入部品費＋外注費＋その他経費 ＝ 製造原価（自動計算）
   → 金額を手動修正した場合は修正前・修正後・理由を必ず記録
        ↓
④ 価格提案（価格提案タブ）
   基準粗利率＋各種加算/調整 → 推奨粗利率
   売価 ＝ 原価 ÷（1 − 粗利率）で推奨売価を算出（自動確定しない）
        ↓
⑤ 担当者決定（価格提案タブ）
   担当者が最終粗利率 / 最終価格を設定し、変更理由を入力して保存
   → AI推奨値・最終値・差分・理由・担当者・日時を PriceDecision に記録
        ↓
⑥ 見積確認（見積確認タブ）
   原価内訳・推奨価格・決定価格・類似案件・注意事項を一覧確認
   → ステータスを「承認待ち」→「見積提出済」へ
        ↓
⑦ 受注 / 失注の登録（見積確認タブ）
   結果と受注価格を記録 → 過去見積として検索対象になる
```

## 6. MVP で実装する範囲（今回）

1. 案件登録（案件ID自動発行）
2. PDF アップロード（ローカル保存）
3. 図面解析（AI 抽象化層＋Mock/Gemini/OpenAI、結果の編集・保存）
4. 原価マスタ 4 種の CRUD
5. 原価計算（プログラムロジック、内訳表示）
6. 手動修正＋修正理由の履歴保存
7. 粗利提案（基準率＋加算項目 → 推奨粗利率・推奨売価）
8. 担当者による最終決定＋差分・理由の保存（経験値データ化）
9. 見積確認画面（類似案件の簡易表示を含む）
10. ステータス管理・案件一覧
11. ダッシュボード（簡易集計）
12. 過去見積検索

## 8. 計算仕様

### 8.1 原価計算（`src/lib/cost.ts`）

```
材料費   = Σ(材料明細: 数量 × 単価)
加工費   = Σ(加工明細: 数量 × 単価)      ※数量 = 時間(分)・回数など課金単位に応じた値
購入部品費 = Σ(購入部品明細: 数量 × 単価)
外注費   = Σ(外注明細: 数量 × 単価)
その他経費 = Σ(その他明細)
─────────────────────
製造原価 = 上記合計
```

- 明細行の金額は自動計算だが、行単位で手動上書き可能（source = manual）
- 手動修正時は `CostAdjustmentLog` に修正前 / 修正後 / 理由 / 担当者 / 日時を保存

### 8.2 売価計算（`src/lib/pricing.ts`）

```
推奨粗利率 = 基準粗利率 + 小ロット加算 + 短納期加算 + 特殊加工加算
           + 難易度加算 + リスク加算 + 顧客別調整 + 営業調整 + その他調整

売価 = 原価 ÷ (1 − 粗利率)          ※粗利率は 0〜95% にクランプ
端数 = 1円未満切り上げ
```

例: 原価 70,000 円、粗利率 30% → 売価 100,000 円

## 9. 仮定事項（実業務に合わせて要調整）

一般的な製造業（板金・機械加工系）の見積業務を仮定して構築した。以下は仮定であり、実際の業務フロー・原価計算ルールに合わせて変更する前提の設計にしてある。

| # | 仮定 | 変更する場合の箇所 |
|---|---|---|
| A1 | 案件IDは `Q-西暦-連番4桁`（例 Q-2026-0001）。年ごとに連番リセット | `src/lib/project-id.ts` |
| A2 | 原価カテゴリは「材料費 / 加工費 / 購入部品費 / 外注費 / その他経費」の5分類。間接費・段取り費は「その他経費」に含める | `src/lib/cost.ts` の `COST_CATEGORIES` |
| A3 | 加工費の数量は課金単位（分 / 回 / 個）に応じた値を担当者が入力する（加工時間の自動見積はしない） | 原価計算タブ |
| A4 | 材料費は「数量 × 単価」の単純積。歩留まり・スクラップ控除は考慮しない | `src/lib/cost.ts` |
| A5 | 粗利率はマークアップ率ではなく売価基準（売価 = 原価 ÷ (1−粗利率)） | `src/lib/pricing.ts` |
| A6 | 粗利加算項目は固定の8種（小ロット / 短納期 / 特殊加工 / 難易度 / リスク / 顧客別 / 営業 / その他）＋自由入力の理由 | `MarginProposal` モデル |
| A7 | 類似案件は MVP では「同一顧客 or 材質一致 or 品番部分一致」の単純ルールで抽出。AI 類似検索は第2フェーズ | `src/lib/similar.ts` |
| A8 | ユーザー認証なし（社内ネットワークでの利用を想定）。担当者名はテキスト入力 | 第2フェーズで認証追加 |
| A9 | 消費税は扱わない（見積金額は税抜） | 第2フェーズ |
| A10 | 図面は PDF 1ファイル/案件。差し替えは再アップロードで上書き | 案件登録・詳細画面 |
| A11 | ステータスは手動変更（自動遷移は解析実行時の「図面解析中」→完了時「原価確認」のみ） | `src/lib/status.ts` |
| A12 | AI へ送信するのは「図面PDF本体＋案件名・数量」のみ。顧客名は送信しない | `src/lib/ai/` |
